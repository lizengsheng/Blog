## 目录

## 学习目标

- 用最小循环解释 Agent 与固定工作流的区别；
- 将模型、工具、状态和控制流拆成边界清晰的组件；
- 为超时、重试、重复调用和人工介入设计可恢复语义；
- 用轨迹和任务结果评估系统，而不是只评价最后一句回答。

## 1. 从 ReAct 循环开始

[ReAct](https://arxiv.org/abs/2210.03629) 将推理轨迹与面向环境的行动交错起来。工程上可以把最小循环写成：

1. 读取目标、上下文和当前状态；
2. 模型选择回答、调用工具或结束；
3. 系统校验并执行动作；
4. 将观察结果写回状态；
5. 在预算、终止条件或人工中断前继续循环。

关键点不在于循环有多少行代码，而在于每一步是否可验证、可追踪、可恢复。

## 2. 从循环升级为执行图

[LangGraph 的 Graph API](https://langchain-ai.github.io/langgraph/how-tos/state-reducers/) 将流程描述为 State、Nodes 和 Edges。这个抽象适合表达条件分支、循环、并行、检查点和人工审批，也让确定性代码与模型决策可以处在同一张执行图中。

计划拆分的核心节点：

- **输入规范化**：明确目标、约束与可用资源；
- **规划/路由**：决定下一步节点，而不是直接执行副作用；
- **模型调用**：固定输入输出 schema，记录模型与采样配置；
- **工具执行**：校验参数、权限、超时和幂等键；
- **结果审查**：判断是否完成、重试、降级或转人工；
- **状态持久化**：保存足以恢复执行的检查点。

## 3. 工具不是函数列表，而是安全边界

每个工具至少需要定义：输入 schema、输出 schema、错误类型、超时、是否有副作用、幂等策略和权限范围。只把函数描述交给模型，会把系统正确性押在一次自然语言生成上。

需要特别覆盖的失败模式：

- 参数合法但业务语义错误；
- 外部服务限流或部分成功；
- 重试导致重复写入；
- 工具返回内容过长或包含提示注入；
- 模型在循环中反复选择同一无效动作。

## 4. 状态、记忆与上下文不是同一个概念

- **执行状态**：本次任务当前走到哪里，应可检查点恢复；
- **短期上下文**：模型本轮决策需要看到的信息，应受 token 预算约束；
- **长期记忆**：跨任务复用的信息，需要来源、时效和删除策略；
- **业务数据**：系统事实来源，不应因为模型总结而失去原始记录。

后续实现需要验证“压缩上下文”是否保留了做出下一步决策所需的证据，而不是只追求更短。

## 5. 可观测性与评估

一条可调试轨迹至少应记录 run、thread、节点、模型调用、工具调用、延迟、token、错误和状态版本。[Agent Protocol](https://langchain-ai.github.io/agent-protocol/) 将 Runs、Threads 和 Store 作为服务 Agent 的核心概念，可作为接口设计参考。

评估分为三层：

1. **结果层**：任务是否完成、答案是否满足约束；
2. **轨迹层**：工具选择、步骤数、成本和恢复是否合理；
3. **系统层**：延迟、成功率、重试率和人工接管率是否达标。

## 最小原型计划

- 实现一个带两种只读工具的单 Agent；
- 用类型化状态描述输入、观察和最终结果；
- 加入最大步数、超时、幂等键和检查点；
- 保存完整轨迹并构造成功、超时、工具错误、循环四类测试；
- 对比自由循环与显式执行图在可恢复性和调试成本上的差异。
